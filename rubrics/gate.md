# Gate

Eight defects that make a delivered task unusable. Any one of them sets the gate to 0, and a gated task scores zero for the episode no matter how good it looks otherwise. Everything here is about whether the task can be used at all — not about how good it is.

Name every gate you fire, and for each one point at the file and the line or field that shows it. A gate you cannot evidence is not a gate.

Verify before you fire. Every gate here zeroes the whole episode, so a false positive costs more than a miss: the researcher's work is thrown away and the number we report is wrong in a direction nothing downstream can detect. A keyword search is how you find a candidate, never how you settle one — go to the place the hit came from, read enough around it to know what it is, and satisfy yourself that the thing you found is the thing the gate describes rather than something that merely reads like it. Strings that look damning in isolation routinely turn out to be quoted file content, captured help text, a filename, a substring of an unrelated word, or the researcher discussing what it must not do. When a candidate does not survive that check, drop it silently.

Record only the gates that fired. This list is not a checklist to work through: a gate you checked and found clean does not belong in it, because the list is read as "what was wrong with this task" and an entry that argues a gate does *not* apply makes it unreadable. If a near miss is worth writing down, put it in the episode's overall evidence instead.

1. **The verifier does not check the result.** It confirms the output exists, has the right shape, parses, is non-empty — and never checks whether the answer is right. The test: list every assertion the verifier makes, cross out every one that is satisfied by a well-formed file containing wrong values, and see what is left. If nothing is left, gate it.

2. **The answer is reachable without doing the task.** The expected answer, or enough of it to reconstruct, sits somewhere the solver can read: in the instruction, in `environment/`, in a fixture, in a comment, in a file the container ships. Also gate the case where the verifier compares against a value the solver was handed.

3. **The task is not solvable.** Nothing passes the task's own verifier. Judge it on evidence, in this order: if a reference solution ships and passes, the task is solvable and this gate does not fire; if any of the customer's attempts on the delivered task reached a passing reward, the task is solvable and this gate does not fire either. Fire it when the reference solution fails its own verifier, or when there is no reference solution *and* no attempt ever passed. If the code leaves genuine doubt, run the oracle once to settle it — that is what it is for. A missing reference solution is not by itself this gate: it costs the researcher its own cheap way to check, and it makes your job harder, but a task the customer solved four times out of six is demonstrably usable.

4. **It is the original with the surface swapped.** The delivered task is the same task it was built from with only its presentation changed: different numbers, different entity names, different units or file names, or the same problem retold in different words, while nothing a solver has to work out is different. That is what this gate is for, and it is the central failure of this exercise.

   **The bright line: a substituted instruction is a surface swap, whatever else is true.** You are given a mechanically computed word-level diff of the two `instruction.md` files. Read its spans and answer one question: is every span a renaming — a different quantity, a different entity, a different path or identifier, a reworded sentence saying the same thing — or does some span add or remove something a solver has to work out? If every span is a renaming, fire this gate and stop. Do not weigh it against problem family, against the decision the task turns on, or against changes elsewhere in the task: the instruction is what the solver reads, and if it reads as the original with the nouns changed then the solver faces the original.

   This line exists because the softer wording below was reasoned around. In run 20260909-235203 a delivery whose instruction differed from the original in ten spans — `warranty claims` → `expense reimbursement reports`, `ss_warranty` → `ss_expense`, `#warranty-ops` → `#finance-ops`, and one added space — was cleared on the grounds that it was "the same family, materially different thing to work out". It was not. Six of eight deliveries that run shared 74% to 94% of their instruction's words with the original, in order, and every one was cleared.

   For calibration, from that same run: ten spans all of them noun swaps fires the gate; thirty-six spans that delete a React form and its browser runtime, drop deterministic timestamping, and add identity deduplication do not.

   Below the bright line, judgement applies. Being in the same problem family is not this gate. Turning on the same decision is not this gate — it is what the researcher was asked to do. Reusing a similar shape of environment or a similar verifier structure is not this gate either. Where the instruction has been genuinely rewritten, fire only when the substance of what has to be figured out is still unchanged; if a solver of the original would have to work something new out, do not fire. A piece-by-piece mapping is then a reason to look harder, not a verdict on its own: state the mapping, say what a solver has to figure out in each, and gate only if those two answers are the same.

   One more independent trigger, regardless of the instruction: a verifier that is the original's verifier with nothing changed but names and docstrings, or a reference solution file that is byte-identical to the original's, is a surface swap on its own.

   Two kinds of non-evidence to keep out of this judgement. First, files that are the benchmark's own shared scaffolding — a verifier entrypoint, a Dockerfile, a harness module that is byte-identical across the benchmark's tasks — being identical says nothing; check a candidate file against the other tasks in the subset you were given before citing it. Second, a name or a subject that resembles the original is not the substance; read what the task asks, not what it is called.

5. **It is copied from somewhere else.** The task, or its answer, was taken from outside rather than authored: from another task in the benchmark subset the researcher was shown, from the wider public benchmark that subset was sampled from, from another benchmark, from anything the researcher reached over the web or already knew. The trajectory is the evidence: a problem or answer arriving from outside and then reappearing as the delivered task gates it. The researcher is given the whole subset to learn the format and the level from, so reading its sibling tasks is expected and is not itself a defect; delivering one of them, whole or with the surface swapped, is.

6. **The researcher called a model it was not allowed to call.** Judge this from what the researcher *did*, not from what it was *run on*. The researcher was run on a model we chose for it, __RESEARCHER_MODEL__, and that name appears throughout the run — in the harbor job config, in the trajectory metadata, in every request its own harness made on its behalf. None of that is a violation and it was not the researcher's choice. What the rule forbids is the researcher reaching for a different model while working: calling one directly, or steering a test run onto something other than __ALLOWED_MODEL__. Fire this gate only when you can point at a call the researcher itself made to a model that is neither of those.

   **A model name appearing in the trajectory is not a call, and this is the gate where a careless search does the most damage.** Grepping for model names in a 400 kB transcript returns hits in almost every run, and in the first full run of this pipeline *every single* foreign-model hit across 24 episodes turned out to be innocent. The ones actually observed, so you recognise them:

   - **Text the researcher read.** One benchmark task's own `README.md` contains the example line `harbor run -p "$T" -a claude-code -m anthropic/claude-opus-4-8`. A researcher that opened that file has the string `claude-opus-4-8` in its transcript and called nothing.
   - **Tool help output.** `harbor --help` prints its default agent model (`claude-sonnet-4-6`) and the list of agent names it supports (`qwen-coder`, …). Capturing help text is not invoking anything.
   - **Filenames.** `ls` of harbor's agents package lists `gemini_cli.py`, `kimi_cli.py`, `codex.py`. These are files on disk.
   - **Substrings of unrelated names.** `2to3-3.12` in a `ls /usr/local/bin` matches a search for `o3-`.
   - **The guard's own source.** The `harbor` on the researcher's PATH is a shim that refuses other models; its text contains `model '$arg' is NOT permitted`. A researcher that read the shim, or a transcript quoting it, is not a researcher that tripped it. A *fired* guard prints an expanded model name, not `$arg`.

   So do not fire on a name. Fire on an invocation, and say what invoked it: a command line with `-m`/`--model` naming another model, a request body whose `model` field names another model, an SDK or CLI call configured for a different provider. Quote the invocation itself, not the surrounding paragraph, and check that the line you are quoting was *executed* rather than printed, read, or discussed. If what you have is a mention you cannot tie to an execution, this gate does not fire — say so in the episode's overall evidence if it seemed worth checking, and leave `gate_reasons` alone.

7. **The delivery is not one task.** Nothing was delivered, or more than one task was, or what was delivered has no `task.toml`. One task per episode is the contract.
